## Contract

`AlertDisplayContent` contains an offer key, content revision, title, description, claim URL, source name and attribution URL. It bounds raw strings, rejects malformed UTF-16/control input and requires bounded HTTPS URLs without credentials, explicit ports or fragments. It has no Mongo codec or automatic conversion from a GamerPower candidate: structural validation does not establish a valid campaign, entitlement, market, timezone or safe claim-link semantics.

`AlertMessageRenderer` accepts an explicit trusted exact-host allowlist and a supplied FreeGamePolicy. It requires matching offer key/content revision, currently eligible evidence, and an enabled free-game subscription for the same store/market. It rechecks both claim and attribution hosts. Host allowlisting is a display-link boundary, not approval of every path/query on a host or a network egress policy. The future certified content provider must verify link semantics and ensure content and evidence belong to the same revision.

RENDER-01: the inactive English template is versioned as `free-game-en-v1`. It is an implementation option, not an approved launch language/default. The embed contains the bounded title linked to the claim page, description, store, market, deadline and an active source-attribution link. Unknown ends are displayed explicitly only when the supplied policy permits them. There are no remote images, attachments, components, replies or provider-controlled mention settings.

Text escapes Discord formatting and mention syntax, removes format/bidirectional controls and breaks scheme-based raw URL autolinks. Display truncation preserves full Unicode code points and complete escape sequences. Raw limits are title 256, description 4,000 and source name 128 UTF-16 units; rendered description is at most 2,048 and title at most 256. These are technical budgets. Attribution URLs and configured role IDs are never silently truncated. Mention content exceeding Discord's 2,000-character message limit rejects preparation; it does not split the event or silently omit roles. A future configuration policy should keep selections within the renderable budget.

Serialized `allowed_mentions` has an empty broad-parse list, no allowed users, `replied_user=false`, and exactly the sorted configured role IDs. The content contains only those role mentions. The existing Subscription validation rejects the guild's everyone role. Empty role sets produce no pings, independently of JDA's default mention settings.

The renderer creates an immutable `FrozenMessage` with canonical JSON (sorted object keys and role IDs), an explicit nonce, fresh defensive byte arrays and a SHA-256 of the exact UTF-8 envelope. The nonce must be 1–25 ASCII letters/digits/underscores/hyphens, a deliberate subset of JDA's nonce contract. Callers supply a distinct attempt ID on each attempt and one stable nonce per delivery job, reused on retries after proven nonacceptance; different jobs use distinct nonces. Construction does not generate or persist uniqueness. NEXT-09 adds mandatory offer key, subscription ID and destination/incarnation to PreparedPayload, alongside content/subscription revisions, template version and approved roles. Authorization checks those identities even when revisions and roles match. Rendering itself is never permission to send.

Future transport must preserve this envelope, including nonce and mention fields. Rebuilding it with different fields, order or defaults changes the exact-byte hash and requires a reviewed adapter contract. A nonce is not a durable exactly-once guarantee. No `enforce_nonce` or Discord deduplication behavior is claimed here. A later retry after definite nonacceptance must reload/re-render/re-authorize; uncertain attempts remain quarantined under the existing rules.
